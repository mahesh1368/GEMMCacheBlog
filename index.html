Introduction

Why GEMM exposes everything wrong with your memory access pattern

General Matrix Multiplication (GEMM) — computing C = A × B — is among the most fundamental operations in computing. It drives deep learning inference, scientific simulation, graphics pipelines, and signal processing. But despite its apparent simplicity, a naive implementation on modern hardware can be devastatingly slow.

The culprit is the memory hierarchy. Modern processors are fast; their caches are small; DRAM is slow. A naive GEMM thrashes the cache spectacularly. This post documents exactly what happens when you take that naive code and systematically fix it — measured on a Raspberry Pi 5 with ARM Cortex-A76 cores, using hardware performance counters and Neon SIMD intrinsics.

"The memory wall is real. Every algorithm you write is negotiating with the cache — whether you know it or not."

We explored five distinct approaches: naive, loop-reordered, scalar tiling at four block sizes, and SIMD-accelerated tiling at the same four block sizes. The results tell a clear, quantitative story.

01
The Starting Point

Naive GEMM — A Cache Demolition Derby

The straightforward three-loop formulation iterates i over rows of A, j over columns of B, and k over the shared dimension. The innermost access pattern for B is B[k][j] — stepping through an entire column, one element per row. In row-major memory layout, this is the worst possible access: every element is a full row-stride apart, virtually guaranteed to be a cache miss.

// Naive: i → j → k (column-major access on B) for (int i = 0; i < N; i++) for (int j = 0; j < N; j++) for (int k = 0; k < N; k++) C[i][j] += A[i][k] * B[k][j]; // ← cache hostile!

With a 45% cache miss rate, the processor spends most of its time waiting on DRAM. The IPC of 0.218 — barely a fifth of an instruction per cycle — tells the story: the CPU is almost entirely stalled. It's less a computation and more a waiting exercise.

At 45% miss rate, the Cortex-A76's out-of-order engine has almost nothing to speculatively execute. The memory bus is the bottleneck, not the arithmetic units.

02
Loop Reordering

The 29× Fix That Took One Minute

The fix is almost offensively simple: swap the j and k loops. This changes the innermost access to B[k][j] traversed row-by-row — sequential memory — instead of column-by-column. The cache prefetcher can now do its job.

// Reordered: i → k → j (row-major access on B) for (int i = 0; i < N; i++) for (int k = 0; k < N; k++) for (int j = 0; j < N; j++) C[i][j] += A[i][k] * B[k][j]; // ← now cache friendly!

03
Cache-Aware Tiling

Blocking for the L1/L2 Cache Hierarchy

Loop reordering helped A and B considerably, but the update C[i][j] still scatters writes across a large matrix. Tiling (blocking) constrains the working set to fit within the cache at any moment — the core idea is to process small B×B sub-matrices at a time, so all three matrices A, B, and C stay hot in cache during computation of that tile.

// Tiled: 6 nested loops — tiles then elements for (ii = 0; ii < N; ii += BS) for (kk = 0; kk < N; kk += BS) for (jj = 0; jj < N; jj += BS) for (i = ii; i < ii+BS; i++) for (k = kk; k < kk+BS; k++) for (j = jj; j < jj+BS; j++) C[i][j] += A[i][k] * B[k][j];

We tested four block sizes (BS = 4, 8, 16, 32) to understand how different tile sizes interact with the L1 and L2 cache sizes on the Cortex-A76.

Scalar tiling — latency and cache miss rate by block size
Block size 4: 8.27s, 1.2% miss. BS=8: 5.2s, 1.9%. BS=16: 4.3s, 8.6%. BS=32: 2.82s, 8.5%.

The pattern is interesting: smaller block sizes (BS=4, BS=8) achieve dramatically lower cache miss rates (1.2%–1.9%) because the tile fits comfortably in L1 cache. Larger blocks (BS=16, BS=32) see miss rates creep back up to 8–9% as tiles spill into L2, yet still run faster — because the arithmetic intensity improvement outweighs the cache penalty. BS=32 at 2.82 seconds represents a 35× speedup over naive.

At BS=4, the cache miss rate drops to 1.2% — 38× better than naive. The working set (3 tiles of 4×4 floats = 192 bytes) fits entirely in L1 with room to spare.

The IPC jump tells the story

Where loop reordering brought IPC from 0.22 to 1.19, tiling pushes it to 3.49 at BS=4. The CPU can finally keep its execution units fed. The arithmetic units are no longer waiting for cache fills — they're computing.

04
NEON SIMD Vectorization

Exploiting the Cortex-A76's Neon Engine

Tiling improved cache behavior. But each multiply-accumulate still operated on single floats. The Raspberry Pi 5's Cortex-A76 cores have 128-bit Neon SIMD units capable of processing 4 single-precision floats simultaneously. Adding SIMD to our tiled loop should multiply throughput — if we can keep the units fed.

// Neon SIMD inner loop (BS=8 example) float32x4_t va = vdupq_n_f32(A[i][k]); float32x4_t vb = vld1q_f32(&B[k][j]); float32x4_t vc = vld1q_f32(&C[i][j]); vc = vfmaq_f32(vc, va, vb); // fused multiply-add × 4 vst1q_f32(&C[i][j], vc);
Scalar tiling vs NEON SIMD tiling — latency by block size
Scalar vs SIMD: BS4 8.27 vs 5.06s; BS8 5.20 vs 4.34s; BS16 4.30 vs 3.92s; BS32 2.82 vs 3.06s.

SIMD brings consistent latency improvements across BS=4, 8, and 16. Interestingly, at BS=32 the SIMD version is marginally slower — likely due to increased register pressure and slightly worse cache behavior from SIMD loads that span cache line boundaries at that tile size.

The IPC–latency tradeoff

SIMD introduces a subtle dynamic: instructions become wider but the IPC metric (instructions per cycle) can appear lower because each vector instruction does more work per "instruction" counted by the hardware. The BS=4 SIMD case nearly matches scalar IPC (3.49 vs 3.49) while running in 61% of the time — pure throughput win.

The best latency SIMD result is BS=4 at 5.06s vs BS=4 scalar at 8.27s — a 1.6× speedup from vectorization alone, on top of tiling's gains over loop reordering.

Conclusions

What the Data Actually Teaches Us

1
Lesson one
Memory access patterns are the first optimization frontier

A single loop reorder — zero algorithmic complexity change — delivered a 29× speedup. No compiler flag, no hardware trick, no clever math. Just fixing the access order. This is the most dramatic result in the entire experiment.

2
Lesson two
Cache miss rate and latency are not the same thing

BS=4 scalar achieves the best cache miss rate (1.20%) but is slower than BS=32 scalar (2.82s). Larger tiles amortize loop overhead and improve arithmetic density even as they stress the cache more. Optimizing for cache miss rate alone is incomplete.

3
Lesson three
SIMD is powerful but not unconditional

SIMD helps at BS=4/8/16 but is marginally counterproductive at BS=32. Vector loads and register pressure interact with tile granularity. Tuning block size and SIMD width together is essential — one cannot be optimized in isolation.

4
Lesson four
IPC is a signal, not a goal

Naive GEMM has an IPC of 0.218 — the CPU is almost entirely stalled. SIMD tiling at BS=4 reaches IPC 3.49. But SIMD's wide operations make each "instruction" count more work, so IPC comparisons across scalar/SIMD are apples-and-oranges. Always look at wall-clock latency.

Cumulative improvement journey
Latency drops from 98.7s naive to 3.4s loop reorder, then tiling brings it to 2.82s scalar and 3.06s SIMD.

The journey from 98.7 seconds to under 3 is almost entirely a story of feeding the cache correctly. SIMD helped, but the single largest gain came from a two-line fix that made the memory access pattern sequential. Modern hardware is extraordinary — but only if you let it work with the cache, not against it.

The Raspberry Pi 5's Cortex-A76 is a capable out-of-order superscalar core — but even it cannot overcome a 45% cache miss rate. Respect the cache hierarchy, and the hardware will reward you generously.
